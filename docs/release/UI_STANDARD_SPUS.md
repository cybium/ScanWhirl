# ScanWhirl Professional UI Standard (SPUS) v1

**Binding release standard | Owner rule: 21 November 2026 | Research checked: 21 November 2026**

## 1. Authority and outcome

**No Play upload, including an internal or closed-testing upload, until the exact release candidate passes SPUS v1.** Sideloading an authorised separate demo/test package for these checks is allowed. This implements the owner's newer rule and supersedes older advice that an AI judge, a numerical aesthetic opinion or green CI alone makes the app ready to upload.

SPUS is ScanWhirl's own professional acceptance standard, grounded in the recognised sources below. It is **not** a Google, W3C, ISO or NN/g certification. There is no invented universal “professional UI score”. The named release grade is **SPUS v1 PASS**, **FAIL** or **NOT VERIFIED**. There is no weighted total in which a pretty screen cancels an inaccessible button.

The ambition is to equal or beat the best measured competitor on **each parameter**, not merely average better across the app. Limited release tolerances are defined in section 3; passing within a tolerance must not be described as ranking first.

This document defines tests, not results. **No candidate, competitor ranking, user result or phone PASS is established by writing it.** Existing v4 concept renders and edited store images are not runtime evidence. Keep ScanWhirl's mark, documents-first library and offline-first English/Hindi product; do not copy competitors' cloud, ads, accounts or security policies.

| [NN/g 10 usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/), 1994 set, page reviewed 30 January 2024 | All ten heuristics, evaluated separately against actual tasks and states | Heuristics are qualitative diagnostic principles, not a validated 100-point grading scale. |

Public catalogue checked; no claim to have audited the paid full standard. |

**All density limits, time budgets, icon tolerances, SUS release cutoffs and competitive margins below are explicit SPUS policy choices**, unless identified as an external requirement. They must be frozen before measuring, not altered after seeing ScanWhirl's scores.

Material details: [dialog guidance](https://m3.material.io/components/dialogs/guidelines), [bottom sheets](https://m3.material.io/components/bottom-sheets/guidelines), [type scale](https://m3.material.io/styles/typography/type-scale-tokens), [icons](https://m3.material.io/styles/icons/applying-icons), [target structure](https://m3.material.io/foundations/designing/structure). Direct page extraction returned no body for three M3 pages; their current guidance was independently retrieved through Context7's official M3 corpus. M3 specifies brief clear dialog purpose and meaningful confirmation verbs; **it does not prescribe SPUS's word limits**. Basic dialogs have at most two actions. Modal sheets can present longer action lists; use a page rather than a cramped dialog for a long form.

## 3. Fair comparison and margins

### Fixed comparison panel

Adobe Scan, Microsoft Lens, Genius Scan, CamScanner, Smallpdf and vFlat. Record Android package, displayed version/versionCode, install source/date, Free/paid tier, account requirement, language availability and offline capability for all six. Install only through owner-approved legitimate sources. **Do not assume every named app is currently installable or functional.** For an unavailable/retired app, retain an official availability notice or owner-recorded store result; never obtain an unsafe old APK or silently replace it.

For each parameter, define the best eligible competitor **B** as its best measured outcome among the six on the same physical phone, same language/font condition, same synthetic file hashes and same start/end state. Use the best per metric, not one favourite app overall. Compare only equivalent correct outcomes and tiers; record Free first and approved paid results separately. Never purchase a subscription without owner approval. Log paywalls and unsupported tasks as “unsupported/blocked”, not zero-second successes. Do not reward skipping confirmation, leaking Vault previews or damaging output to save taps.

Every competitor must have a result, a supported/non-supported determination or evidence of unavailability for every applicable row. If a supported, obtainable comparison is simply unmeasured, the comparison is **NOT VERIFIED**, blocking PASS. If no competitor offers a particular task (for example local Vault/backup), retain the six-app capability matrix, apply the absolute threshold, mark ranking **not comparable**, and make no best-in-class claim for that task. An unavailable Lens does not make all other evidence unusable, but a literal six-app live ranking cannot then be claimed.

### Exact release tolerance (apply to every metric separately)

| Metric direction/type | Best-in-class target | Largest permitted gap for SPUS PASS |
|---|---|---|
| Time, including median and tail startup/task time | ScanWhirl <= B | <= B + max(10% of B, 0.2 seconds) |
| Tap/navigation count | ScanWhirl <= B | <= B + 1 tap; gestures and typing episodes separately must not increase by >1 |
| Task success or comprehension percentage | ScanWhirl >= B | >= B minus 5 percentage points |
| SEQ, 1–7 | ScanWhirl >= B | >= B minus 0.3 |
| SUS, 0–100 | ScanWhirl >= B | >= B minus 3 points |
| Subjective quality, anchored 1–5 | ScanWhirl >= B | >= B minus 0.5 |
| Janky-frame percentage | ScanWhirl <= B | <= B + 1 percentage point |
| Defect counts, density-cap violations, safety/trust/accessibility failures | ScanWhirl <= B (usually zero) | **Zero extra failures**; no competitor failure relaxes an absolute limit |
| Size/label/contrast conformance | 100% compliant, >= best competitor's compliance rate | Zero compliance gap. Do not maximise hitbox size or contrast ratio at the expense of layout; compare compliance, not arbitrary largest numbers. |
| Words/lines below the density caps | Less unnecessary reading with equal comprehension | Caps and zero unnecessary/duplicated sentences are binding; compare task time, SEQ and comprehension using their margins, not “fewest words wins” |

Absolute limits always apply even if all competitors fail. A baseline B=0 does not permit a nonzero safety defect. Report “within release margin, not first” wherever ScanWhirl trails B. Retain both best and worst case, all repetitions and failures; never replace a slow run with a faster retry.

## 4. Test setup and evidence

The owner's own phone agent performs ADB work; this standard is not permission for the lead to operate the phone or owner's browser. Owner approves exact serial, test package and fictional fixture directory first. Never uninstall/reset the production app, capture personal Gallery/media, weaken FLAG_SECURE, or read signing secrets.

1. **Freeze the build:** Git SHA, APK SHA-256, package, version, build mode, CI URL and build-to-source provenance. Use release-equivalent optimisations; a demo/test build needs documented differences and retest of affected release behaviour. No Play upload is needed to sideload the candidate.
2. **Freeze the phone:** exact model, Android build, RAM, free storage, pixel size, effective density from `wm density`, refresh rate, brightness, battery saver, thermal condition and animation settings. Primary device must represent a budget Indian phone (record actual specs, preferably 3–4GB RAM). Additional supported-OS/device checks remain required by the normal release gate; one phone does not prove all Android devices.
3. **Freeze data:** one printed A4 fictional page with unique text; three-page 1–3MB image PDF demonstrably compressible to <=200,000 bytes; one clear Hindi page with a reviewed 100-word transcript; a fictional share PDF; one fictional Vault document; library of 100 synthetic documents in named folders. Hash digital fixtures. Same print, distance (30cm), light (300–500 lux), camera orientation and tripod/stand position for scan comparisons. Retain an impossible-size fixture and invalid/password PDFs for negative tests.
4. **Freeze conditions:** EN and HI separately, font scales 1.0, 1.3 and 2.0, portrait and landscape, supported themes and system light/dark settings, button and gesture navigation, keyboard open/closed. Record warm-up and first-run states separately. Airplane-mode tests after any disclosed initial module preparation; also test missing module on first use without pretending it can work offline.
5. **Coverage:** start from `tools/atlas/run_atlas.ps1` and its atlas; enumerate **every reachable screen, sheet, dialog, menu, result variant and Pro gate**. Capture every distinct layout in each language/font setting, and empty, populated, working, error, cancelled, success and target-miss variants where they exist. Use reusable component evidence only with an explicit instance inventory; do not sample away unique strings, backgrounds or exceptions.
6. **Evidence paths:** use a private root `SPUS/<candidate-sha>/<app-code>/<EN-or-HI>/<font>/<state>/`. Each ledger row stores parameter ID, screen/task, raw value, unit, threshold, B and competitor version, gap, verdict, screenshot PNG path, XML path, raw timing/log path, fixture hash, evaluator/date and issue link. Keep original screenshots unedited; blind copies may mask only identifying branding, never content being graded.

**Secure screens:** screenshots may correctly be blocked. Use redacted synthetic-only UI hierarchy plus signed human observation, state/action logs and the identical shared-component evidence for dimensions/contrast. Use read-only resource/layout inspection if necessary, tied to the exact binary. UIAutomator is not guaranteed to expose secure content. If a unique secure control cannot be objectively verified, mark it NOT VERIFIED; never disable screen protection to make a screenshot.

### Measurement methods (reused by the parameter table)

| Code | Exact phone method and limitations |
|---|---|
| M1: hierarchy and geometry | After focus guard confirms authorised package, `adb -s SERIAL shell uiautomator dump /sdcard/Download/SPUS/window.xml`, then pull that one file. Read visible text, content descriptions, clickable nodes, roles/state and bounds. Width/height in dp = pixel extent / (effective dpi / 160). Use the **effective clickable ancestor/TouchDelegate**, not the 24dp glyph alone. Confirm boundary taps and Accessibility Scanner; XML rectangles alone do not prove an expanded hit area. Test all edges and overlaps. Missing nodes require manual/inspector evidence, not presumed PASS. |
| M2: images, words and tokens | Use focus-guarded screenshots plus XML, reading order and the screenshot's actual line breaks. Count whitespace-delimited words in EN/HI (punctuation alone is not a word); count each text once even if exposed through nested nodes. “Before first action” means title + explanatory/help text before the first enabled meaningful choice/primary action; count all explanatory copy, including collapsed copy needed for consent. Exclude fictional document content, filenames and required input values, but log them separately. Count repeated exact sentences after Unicode/whitespace normalisation; two graders flag semantic duplicates. Measure spacing in dp from image/density; typography tokens from a read-only token inventory checked against the displayed screenshot, not guessed sp from pixels. |
| M3: contrast | Save lossless native-resolution PNG, record foreground/background sRGB triplets and pixel coordinates for every text/icon/boundary state and background pairing. Use solid glyph interior pixels, not anti-aliased edges; gradients use the worst adjacent background. Linearise each channel c: c/12.92 if c<=0.04045, otherwise ((c+0.055)/1.055)^2.4; L=0.2126R+0.7152G+0.0722B; ratio=(Llight+0.05)/(Ldark+0.05). Retain calculation file and coordinates. If glyph too thin or colour ambiguous, verify actual rendered colour against resource/state evidence; do not choose favourable edge pixels. Accessibility Scanner findings supplement, not replace, manual checks. |
| M4: timed journey | Stopwatch or timestamped screen recording on synthetic non-secure flows; for secure flows use observer stopwatch/event log without secrets. Start when task card is read and Home is ready; end only at verified successful output. Count each tap, long press, swipe, Back and text-entry episode separately. Total taps include system pickers and permission prompts; record OS-only taps separately. Do not count individual keyboard characters as navigation taps, but retain their entry time. Report trained-operator median plus nearest-rank p90 over 5 measured runs (p90 is max for n=5); one practice run logged separately. Failed runs remain failures and receive the task timeout in the all-attempt timing summary; report success-only time separately. |
| M5: accessibility | Run Google Accessibility Scanner on every capturable state; manually verify all findings. Walk all six tasks with TalkBack in EN/HI, including status announcements, names/roles/selected states, reading order, crop corners, dialogs, focus return and error recovery. Also operate with external keyboard/switch-equivalent navigation where available. Test no focus trap, no obscured focus, no drag-only essential action, no colour-only meaning, and Remove animations. Repeat layout at 100/130/200% font, verifying actual setting (Android nonlinear scaling means glyph sizes need not literally double). Restore phone settings afterwards. |
| M6: performance | With no work pending, run 10 process-cold launches per app/locale, alternating/randomising app order. `adb -s SERIAL shell am start -S -W -n PACKAGE/LAUNCHER` provides TTID proxy (`TotalTime`, cross-check displayed activity log). Separately stopwatch launch to rendered library + responsive Scan/search (observable ready time, not falsely labelled instrumented TTFD). Record one-time setup/download time separately. For scrolling, reset `adb -s SERIAL shell dumpsys gfxinfo PACKAGE reset`; perform the same 10 up/down 500ms swipes through the 100-document library; collect `adb -s SERIAL shell dumpsys gfxinfo PACKAGE framestats`. Repeat 3 times, collect >=300 valid frames each, retain per-frame values and invalid flags; calculate missed-deadline fraction using fixed refresh budget and p95 duration. No live recording/Scanner overhead during timing. If renderer is not covered by gfxinfo, use Perfetto/FrameTimeline with owner agent; missing coverage is NOT VERIFIED, not zero jank. |
| M7: human review | Two independent graders assess the same frozen evidence without seeing each other's verdict. Score each anchored criterion 1–5: 1 blocks/misleads, 2 major confusion or repeated defects, 3 works but needs explanation/visible inconsistency, 4 clear with only minor non-task-affecting defects, 5 immediately clear and no observed defect. Every score needs screenshot path (or secure-screen observation path), cited criterion and concrete finding. Use section 8 adjudication. |

Command examples describe a preapproved test session only. The owner's agent must create the dedicated fixture/output directory safely and verify current command help. Do not capture whole-device private logs. Pixel contrast and XML cannot replace TalkBack and native Hindi review.

Timing precision: verify <=100ms tap acknowledgement with timestamped input/render trace or >=120fps external video of a synthetic, non-secure interaction; an ordinary hand stopwatch cannot prove this limit. Gfxinfo retains a limited recent-frame buffer on some devices: collect numbered chunks during the swipe sequence, deduplicate by frame timestamps, and verify >=300 distinct valid frames rather than assuming one final dump contains the whole run. Record frame duration as `(FrameCompleted - IntendedVsync) / 1,000,000` milliseconds where those fields are valid; exclude only documented nonzero-flag/invalid records, publish exclusions, and use the platform deadline fields/FrameTimeline when available. Record nearest-rank percentiles (`ceil(p*n)`), frame budget, missed-deadline definition and calculation script version for every app.

**Density safety rule:** do not turn an existing information-rich Tools page into unexplained icons merely to reduce word counts. Density caps concern explanatory decision copy, not the number of documents or tools the app can honestly show. At larger fonts, reading and reachability outrank document-count targets.

**Current policy conflicts cannot be hidden:** Android Core now includes light/dark support, while existing IDENTITY defers a light theme. The applicability ledger must record this as an unmet adopted criterion until resolved by an explicit documented product decision and retest. Do not label it N/A simply because it is inconvenient. Similarly, the standard does not authorise adding cloud backup/account sign-in just because a generic Core guideline mentions them. Record an evidenced offline/security-policy scope departure, human approval and no claim of full Android Core compliance. An unresolved applicable failure blocks SPUS.

### Full-framework ledger requirements

For Android, include consistent experience, app switch/sleep/lock, orientation/state parity, graphics, line length, themes, Back button/gesture, targets/contrast/descriptions, sharing, startup/rendering/stability, and applicable permissions/data/backup/Play-asset items. Classify unrelated audio/video/conversation features with explicit reasons. For long prose use Android's 45–75-character readability guidance where width allows; compact labels and narrow-phone lines are not forced to 45 characters. Record the actual line lengths and rationale.

For WCAG, record every A/AA criterion's applicability through WCAG2ICT, including non-text alternatives; relationships/sequence/orientation; colour/contrast/resize/reflow/spacing; keyboard/traps/timing/flashes; focus/labels; pointer gestures/cancellation/drag alternatives/targets; language/predictability/help; error identification/prevention/redundant entry/authentication; and name/role/value/status. Do not claim AA from a contrast check alone. WCAG AA target minimum is **24x24 CSS pixels with specified exceptions** (2.5.8); 44x44 is AAA (2.5.5). Android **48dp** is SPUS's stronger native touch rule; CSS px, physical px and dp are not interchangeable.

NN/g ledger, one evidence-backed grade each: (1) system status -> row 6; (2) real-world language -> 2/8/10; (3) control/freedom -> 4/6; (4) consistency -> 1/3/4; (5) error prevention -> 6/10; (6) recognition -> 2/3/4; (7) efficiency -> 5; (8) aesthetic/minimalist -> 1/2; (9) diagnose/recover -> 6; (10) help/documentation -> contextual help, recovery and offline module explanation in 6/10. Help must answer the relevant question in <=3 taps and work offline for local tasks.

Hindi checklist: natural everyday Hindi rather than forced transliteration; approved glossary; consistent Scan/Import/size/Copy/Vault terms; accurate consent, negation, recovery and money; Devanagari matras/conjuncts/line height with no added letter spacing; correct file units and numerals; mixed filenames/English abbreviations readable; labels match action/spoken name; error text tells a safe next step; 100/130/200% and landscape review; Hindi-primary users explain the consequence without coaching. Critical = changes consent/safety/money meaning; major = wrong action or prevents understanding; minor = non-blocking style issue. Retain disagreements and resolutions.

## 6. Six task cards: identical outcomes and budgets

These are **product budgets, not published universal UX laws**. Use the same task wording, phone, fixtures and outcome test for all apps. Start from Home with ordinary permissions/module setup complete, 100-document library and no pending work. Measure first-use setup separately, never hide it. Timed novice task cutoff is twice the table's time budget; stop earlier for safety. A hint, wrong endpoint or timeout is not unaided success.

| Task | Task card and verified endpoint | Trained operator hard budget (each locale) |
|---|---|---|

| T2 Import + compress to target | “Import this three-page file. Make a separate copy <=200,000 bytes, keeping all three pages readable and the original.” Set exact target; open output and verify byte count/page count and three marked text regions. Same output criterion, even if competitor uses a quality slider. | <=14 taps; median <=90s, p90 <=120s |
| T3 Hindi OCR read + copy | “Read this Hindi page, copy its text and paste into the supplied local test text field.” Start with same imported unrecognised page; output present, >=95% character accuracy against reviewed transcript after Unicode/whitespace normalisation, all critical names/numbers exact. | <=10 taps excluding character keystrokes; median <=60s, p90 <=90s |
| T4 Share / export | “Export this file to the supplied local test folder, then share it to the local test receiver.” File opens with correct pages/content/name; receiver gets readable URI; cancellation must not say delivered. Use local receiver, not personal messaging recipients. | <=8 taps; median <=30s, p90 <=45s |
| T5 Vault add + open | “Put this fictional file in the already-configured Vault, leave/lock it, then unlock and open it.” Only authenticated access; document readable; public/original-copy consequence is explicit. Initial Vault setup and recovery comprehension tested separately, not optimised away. | <=12 taps plus recorded credential-entry episode; median <=60s, p90 <=90s |
| T6 Backup create | “Create a backup of this fictional library in the supplied local folder. Show where it is and which documents it contains.” Persisted nonempty archive, correct timestamp/included scope; owner agent validates it by restoring to a **separate disposable test environment**, never over production. Archive existence alone is insufficient. | <=12 taps plus recorded secret-entry episode; median <=90s, p90 <=120s |

For T3, character accuracy = `max(0, 1 - Levenshtein distance(reference, recognised) / reference character count) * 100`, using Unicode code points after NFC normalisation and collapsing whitespace runs to one space; preserve all letters, matras, punctuation and digits. Publish reference/output and calculation, and check critical names/numbers manually. For T6, the restore drill is correctness verification outside the timed create interval and must still pass. Record its duration separately.

Separate UI efficiency from output correctness, but both must pass. Impossible-size compression should honestly report a miss, not count as T2 success. Native review fixes the Hindi OCR ground truth before testing. Use identical local receiving/input tools across apps and log their overhead. If a competitor lacks Hindi OCR, local Vault or backup, record unsupported; do not substitute a different task or pretend a cloud upload is an equivalent offline result.

## 7. Real-user gate: owner must run it

- Recruit **5–8 adults who have never used ScanWhirl**, at least 2 Hindi-primary and 2 English-primary, including at least 2 regular budget-phone users. Avoid developers/team members; declare acquaintances and familiarity with competitor apps. Obtain consent; no personal documents. A fluent native Hindi reviewer is a separate qualification, not an AI substitute.
- Owner moderates the frozen six task cards with neutral wording, no demonstration/coaching or praise that steers ratings. Record participant IDs, language, task order, successes, time, actions, errors and help. Rotate task/app order to reduce learning effects. Give breaks; a benchmark of seven apps is not one marathon session.
- After **every attempt**, ask SEQ: “Overall, how difficult or easy was the task to complete?” 1 = very difficult, 7 = very easy. Retain failed-task ratings; ask a neutral reason after ratings <5.
- After each complete app session, administer the **unaltered ten SUS items**, 1–5 agreement. Odd items: response minus 1; even: 5 minus response. Sum and multiply by 2.5 for each participant; then average participants. Do not average individual item scores as though they were SUS.
- Hindi instruments require a documented suitable validated translation where available; otherwise two native reviewers translate/back-translate before freezing, preserve polarity/anchors and disclose that direct comparison with English norms has translation uncertainty. Never silently rewrite SUS to improve the score.
- Freeze denominators: overall success = correct unaided attempts / all assigned attempts, separately per task and language cohort. For n=5, >=80% means >=4/5; for a two-person language cohort, both must succeed to reach 80%. Report counts as well as percentages.
- To claim competitor SUS/SEQ/comprehension parity, obtain **at least five independent first-exposure observations per app and per compared task**, counterbalancing and keeping eligibility constant. The same 5–8 people may test all apps over several short sessions if first exposure and order are recorded; recruit additional matched people if fatigue/familiarity makes that invalid. Unsupported task cells remain explicitly unsupported.
- Report mean, median, individual SUS, task/cohort success counts, dispersion and 95% uncertainty intervals (participant-level SUS interval; binomial task-success interval). Five to eight users is a practical defect-finding release gate, **not proof of statistically significant market leadership**. No “best in India” claim from this sample. Confidence intervals do not excuse failure of a frozen threshold.
- A safety-critical misunderstanding, data loss, false success or inaccessible core task blocks release regardless of high SUS. Retest fixes with fresh first-time users for affected first-use measures; never coach the original group until it passes.

## 8. Bias controls and adjudication

1. **Measurements first.** Compute counts/ratios/timings before looking at subjective grades. Lock fixtures, scripts, thresholds, comparison tier and test plan before results. Version any later change and remeasure all affected apps.
2. Every subjective criterion, including each heuristic, gets **two independent graders**. Prefer two trained humans; a human and a different-family model, or two different model families, may be diagnostic reviewers only. They receive app codes A–G in random order, identical prompts/rubrics and evidence, no previous scores or product advocacy.
3. Mask names/logos in review copies where not being tested; retain an unmasked original and log when visual style reveals identity. Brand/trust wording and live interaction cannot be fully blinded; acknowledge this rather than claim double-blind testing.
4. Two agents using the same model family are **not** independent-family review. Current owner project rules allow GPT-only subagents, so satisfy independence with **human graders** rather than launching a prohibited model. AI cannot certify Hindi naturalness, simulate users, fabricate SUS/SEQ or approve account facts.
5. If grader difference **>1 point on 1–5**, obtain a third independent grader without showing previous scores. Use the median of three and preserve every rationale; otherwise average the two. Any score below 4 or any major/critical issue requires human resolution and fresh evidence, not arithmetic concealment.
6. Each grade links a precise screenshot path per score (or documented secure-screen exception), criterion, observed issue and task impact. No evidence means NOT VERIFIED. All subjective passes require final human signoff; **AI grades never override a measured FAIL**.
7. Owner or independent human reviewer checks raw evidence against a random 20% of measured rows and **all hard failures, N/A decisions and safety-critical rows**. Reconcile discrepancies and expand to 100% of affected measurement type if any material error is found.
8. Keep full trial logs, unavailable/unsupported outcomes, negative evidence and disagreement. No removing the slowest competitor, comparing paid ScanWhirl with a blocked free competitor without disclosure, choosing favourable screenshots, or declaring unrun tests green.

## 9. Exact release decision

**PASS only when all of the following are true:**

1. All parameter submetrics, every six-task/locale result and full-framework applicability ledger are complete; all applicable absolute thresholds pass.
2. Every comparable metric is within section 3's maximum gap from the best measured competitor; target remains equal/better on every metric. Unsupported/unavailable cells have evidence and no false rankings. Any obtainable supported baseline left unmeasured blocks PASS.
3. Both independent graders and required adjudication complete; human accessibility and native Hindi signoff complete; no unresolved major/critical issue.
4. Owner-run 5–8 first-time-user study meets task success, SUS and per-task SEQ thresholds, with competitor evidence for claimed comparative satisfaction.
5. Exact candidate SHA/APK, phone evidence, fixture hashes and CI provenance are linked; normal functionality, security, storage, billing and release gates also pass. SPUS does not replace them.
6. Owner signs the evidence-linked decision. **Only then may the owner separately authorise a Play upload.** Passing is not authorisation to publish.

Any measured breach = **FAIL**. Any missing required evidence = **NOT VERIFIED** (upload blocked equally). There is no “mostly PASS”, no deferring a failed parameter to the next release, no AI or owner gut-feel waiver while still calling it SPUS PASS. A genuine policy amendment needs a new documented version, reasons and full affected remeasurement, not a quiet exception.

Signoff record: standard version; source snapshots/date; candidate SHA/APK hash; phone; baseline app versions/tiers; coverage matrix; ledger path; independent/native/accessibility human reviewers; user-study path and participant counts; failures and resolutions; ranking-vs-margin list; exact decision/date; owner's signature. UI/string/navigation/output changes invalidate affected rows; shared-component changes invalidate all dependent screens. Changed app/phone/fixtures invalidate corresponding competitive comparisons.
